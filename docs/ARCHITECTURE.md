# Architecture notes

```
React UI ──HTTP/JSON──▶ Express (routes → services) ──▶ MongoDB   (metadata: users, folders, files, versions, audit)
                                     └────────────────▶ Storage    (blob bytes under server-generated keys)
```

* **routes/** parse input (zod), authenticate, call services, shape responses.
* **services/access** is the single place permissions are computed; every route goes through `loadItem(kind, id, user, minRole)`.
* **services/fileService, trashService, folderService** hold multi-step operations and their rollback logic.
* **storage/** is the blob interface: `newKey, put, copy, stat, stream, remove`. `LocalStorage` implements it with the filesystem.

## MongoDB schema

| Collection | Key fields | Indexes |
|---|---|---|
| `users` | `email`, `passwordHash` (select:false), `quotaBytes`, `storageUsed` | unique `email` |
| `folders` | `name`, `owner`, `parent`, `ancestors[]`, `shares[{user, role}]`, `trashed`, `trashedWith` | **unique** `(owner, parent, name)` *where trashed=false*; `ancestors`; `shares.user`; `(owner, trashed)`; `trashedWith` |
| `files` | `name`, `owner`, `parent`, `mimeType`, `size`, `currentVersion`, `shares[]`, `link{tokenHash, expiresAt, maxDownloads, downloads}`, `trashed`, `trashedWith` | same unique partial index; `parent`; `shares.user`; sparse `link.tokenHash` |
| `versions` | `file`, `number`, `size`, `mimeType`, `sha256`, `storageKey`, `createdBy` | **unique** `(file, number)` |
| `auditlogs` | `actor`, `owner`, `action`, `targetType`, `targetId`, `meta` | `(owner, createdAt desc)` |

Design choices:

* **Files and folders are separate collections** with their own validation and indexes. The listing endpoints paginate across both (folders first) with one `page/limit`.
* **Versions are their own collection**, immutable, and `files` denormalises `size/mimeType/currentVersion` so listings never join.
  File *contents* are never in MongoDB, only a random `storageKey`.
* **Materialised path (`folders.ancestors`)** makes permission inheritance a single indexed query and "all descendants" a single `{ancestors: id}` lookup.
  Moving a folder rewrites the paths of its subtree with one aggregation-pipeline `updateMany`. Files point only at their direct parent, so they need no rewrite.
* **Duplicate names are enforced by a unique partial index** (live items only), so the rule holds under races; the service also pre-checks to return a friendly 409,
  and checks the *other* collection (a file and folder can't share a name either).
* **Shares are embedded** (`[{user, role}]`) because there are few per item and the check must be a single read. The multikey index powers "Shared with me".

## Permissions

Roles: `viewer < editor < owner`. A user's role on an item is *owner*, or the strongest share on the item or **any ancestor folder**.

| Action | Needs |
|---|---|
| list / read / download / list versions | viewer |
| upload into a folder, new version, restore a version, rename, move, trash | editor |
| manage shares, create/revoke public link, restore from trash, permanent delete | owner |

Rules worth knowing:
* An item the caller cannot see is reported as **404, not 403**, so IDs can't be probed. 403 only appears when the caller can see the item but lacks the role.
* Permissions are checked **before the upload body is read** (folder/file ids and names travel in the URL).
* Moves require editor on both ends, a destination under the same owner, and no cycles; only owners may move to the root.
* Breadcrumbs for a shared folder start at the folder shared with you; ancestor names above it are never returned.

## Files on disk, and upload integrity

Blob keys are `<2 hex>/<uuid>`, generated by the server; user-supplied names are only metadata. `LocalStorage.pathFor` re-validates every key against a strict regex and checks the resolved path stays inside the storage directory (defence in depth against path traversal). Names containing `/`, `\`, control characters, `.` or `..` are rejected; directory parts in uploaded filenames are stripped.
Downloads are always `Content-Disposition: attachment` with `X-Content-Type-Options: nosniff`.

Upload flow (no transactions, so each step is compensated):

1. multer streams the body to `STORAGE_DIR/.tmp` with a hard size limit (413 if exceeded; partial files are deleted).
2. Pre-check for a duplicate name (fast, friendly 409).
3. **Reserve quota atomically**: one `findOneAndUpdate` with `$expr: storageUsed + n <= quotaBytes`; concurrent uploads cannot both slip under the limit (507 otherwise).
4. Atomically `rename` the temp file to its permanent key.
5. Insert the `Version`, then the `File`. The File record only exists once the bytes and version exist.
6. On *any* failure: release quota, delete the blob, delete the version, always delete the temp file. A periodic sweep also removes temp files older than 1 hour.

Deleting data is the mirror image: **database first, blobs second**, so a crash leaves at worst an unreferenced blob, never a record pointing at missing bytes.

## Versions

* `PUT /files/:id/content` appends version *n+1*. Two writers racing for the same number collide on the unique `(file, number)` index; a compare-and-set on `files.currentVersion` is the second guard. The loser gets `409 VERSION_CONFLICT` and is rolled back.
* `If-Match: <n>` makes the update conditional → `412` if the file has moved on.
* Restoring version *k* **appends a copy** as the newest version (history is never rewritten) and is quota-checked like an upload.
* Only the newest `MAX_VERSIONS_PER_FILE` versions are kept; pruned blobs are deleted and their quota released.

## Trash

Trashing a folder marks it and its whole subtree `trashed: true, trashedWith: <folderId>` in one logical operation, so nothing below it is reachable and `/trash` shows only the top-level item (`trashedWith == _id`).
Owner, shares and the original parent are untouched, so **restore** brings back the same tree with the same permissions.
If the original parent is gone or trashed the item returns to the owner's root; if its name was taken in the meantime it is restored as `name (restored)`, never overwriting anything.
Trashed items still count toward quota until permanently deleted (or the trash is emptied).

## Public links

`POST /files/:id/link` returns a random 256-bit token **once**; only its SHA-256 is stored. `GET /public/:token` checks expiry and the download cap in the *same atomic update that counts the download*, and answers 404 identically for unknown, expired, exhausted and revoked links.

## Trade-offs

* **No transactions / sessions**: keeps it runnable on a standalone `mongod`. With a replica set, steps 3-5 of the upload could become one transaction; the compensation code would then be a fallback for blob cleanup only.
* **Local disk storage**: simple and testable; the storage interface is intentionally tiny so an S3 implementation (multipart upload + presigned downloads) is a drop-in.
* **Offset pagination**: simple and fine for folder sizes here; cursor pagination would be better for huge folders.
* **Owner-pays quota** in shared folders: simple accounting; a per-uploader model would need an extra ledger.
